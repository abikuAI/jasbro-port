## Quick answers

**Why doesn't it compile?**
One missing nested class. `Perks.java:3144` references `Buff.AlreadyFull`, which does not exist in
`src/main/java` — the only tree Gradle actually compiles. **One error in 533 files.** The fork's last
commit added that class to `src/jasbro/` (a duplicate tree the build ignores) and mistakenly claimed
it had deleted `src/main`. It never did.

**Is it Flash / JavaScript?**
No — it's **Java** (Swing + Gradle). The script-like content you're thinking of is the game's
XStream-serialized XML: characters, items, events, quests.

**Can it be fixed?**
Yes, and it's proven here. One 4-line class, then it compiles clean and the resulting jar launches.

**Is the repo the same as my working game?**
**No.** The shipped `JaSBro.jar` has **80 top-level classes absent from the repo**, including three
entire packages (`traits/perktrees/`, `gui/town/`, `game/realestate/`). The GitHub repo is an
*older* snapshot than your `R0.1.2 final` game. Fixing the compile error gives you a runnable —
but older — JaSBro.

**So how do I get source for the game I actually have?**
**Done.** Your `JaSBro.jar` was decompiled into **616 `.java` files** that compile with **0 errors**
and run the game with **zero exceptions** — recoverable, not the original author's formatting.
See [`DECOMPILATION.md`](DECOMPILATION.md); the source is in `decompiled/source/`.

## Build it

```powershell
pwsh -File build.ps1 -ApplyFix
```

Compiles all 533 sources with JDK 8 and packages a runnable jar into `build-out/`.
No Gradle needed — all 34 dependencies already ship in the game's `lib/`.

| Flag | Effect |
|---|---|
| *(none)* | compile + package. Fails with a clear message on the known error. |
| `-ApplyFix` | patch `Buff.AlreadyFull` into the repo first, then build. |
| `-Clean` | wipe `build-out/` first. |

Build without the fix to see the failure for yourself:

```
[build] compiling 533 java files

COMPILE FAILED - 1 error(s). Full log: build-out\logs\compile.log
  ...Perks.java:3144: error: cannot find symbol
                      character.addCondition(new Buff.AlreadyFull());
    symbol:   class AlreadyFull
    location: class Buff
  1 error

This is the known issue. Re-run with -ApplyFix to patch it.
```

The patch is applied to your working copy only — **it is not committed**. Review with
`git -C repo diff`, then commit and push when you're happy.

### The port so far

`port/` builds and verifies offline (no NuGet — see `port/nuget.config`):

```powershell
cd port
dotnet run --project Simbro.Verify
```

**113 parity checks, 0 failures.** Covers the `Time` enum cycle, `EventType` (32 values with the
custom-content flag), the money semantics (event-before-mutation ordering, negative balances,
`BROKE`), the attribute type system (53 attribute keys across three families), a `properties.xml`
parser verified **field-by-field against the shipped game's own loader** over all 10 real characters
(506 images, 636 tags), and a save reader/writer verified against golden fixtures produced by the
real Java build — including `Charakter.base` being `transient`, and XStream reference resolution
with 1-based indexing. See [`SAVE-FORMAT.md`](SAVE-FORMAT.md) and
[`CONTENT-PARITY.md`](CONTENT-PARITY.md).

**Compatibility is proven in both directions — and for both content and saves.**

```powershell
pwsh -File verify-save.ps1
```

This regenerates every fixture using the **real Java classes** (including running the game's own
content loader over `C:\Games\Jasbro_Final\characters`), runs the C# verifier against them, then
feeds a **C#-written save back to the shipped Java game** and confirms it reconstructs the values.

Two real bugs were caught this way, neither of which would have shown up in a hand-written test:

- **Image tags are a `HashSet`** — they deduplicate, and their order is a JVM hash artifact rather
  than a content contract. Verified stable across runs, which is exactly what makes comparing order
  a trap.
- **Images are sorted by filename**, and the comparison must be **ordinal** — C#'s default is
  culture-sensitive and would mis-order non-ASCII filenames.

C# enums are **generated** from the decompiled Java by `tools/gen_enums.py`, so the port cannot
drift from the shipped game's constant set (96 `ImageTag`, 372 `Trait`, 18 `SpecializationType`,
8 `Sextype`, 5 `CharacterType`, 3 `Gender`).

## Gotchas on this machine

**TLS is broken.** `Invoke-WebRequest`, `curl.exe`, and even Git's bundled curl all fail with
`SEC_E_NO_CREDENTIALS`. Workarounds that do work:

- **Git:** `git -c http.sslBackend=openssl clone ...`
- **Downloads:** Python's `urllib` (bundles its own OpenSSL, bypasses schannel)

**No JDK was installed** — only `JRE 1.8` at `C:\Program Files\Java\jre-1.8`. A portable JDK 8 and
Gradle 4.10.3 used by earlier work at `%LOCALAPPDATA%\Temp\simbro-gradle\` have had their `bin/`
directories emptied; they're gone. This folder's `tools/jdk8` replaces them.

**No Gradle, no wrapper.** `build.gradle` targets Gradle ~4.x and uses syntax (`compile`,
`archiveName`, `uploadArchives`) that Gradle 7+ rejects. `build.ps1` sidesteps Gradle entirely.
