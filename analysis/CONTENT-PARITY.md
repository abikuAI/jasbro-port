# Content parity — the C# parser vs the real Java loader

*How we know the port reads your character content exactly the way the shipped game does.*

---

## Why this exists

Save compatibility was proven by round-tripping through the real game. **Content** needed the same
treatment, for a different reason.

The port reimplements `properties.xml` parsing in C#. A reimplementation can be *plausible* and
still be *wrong* — it will happily produce a character with the right name and the wrong traits, and
nothing about it looks broken until gameplay diverges hours in.

So instead of writing expectations by hand, we make the **shipped game's own loader** read the real
content and record what it found. The C# parser is then measured against that record.

```
C:\Games\Jasbro_Final\characters\*   (the real content)
              │
              │  fixtures/java/ContentFixture.java
              │  runs the SHIPPED CharacterFileLoader
              ▼
      fixtures/content-golden.txt      (622 lines — the ground truth)
              │
              │  port/Simbro.Verify  compares field by field
              ▼
      Simbro.Core CharacterPropertiesParser
```

**Result: 10 of 10 characters, every field identical** — name, type, gender, initial
specialization, attributes, traits, image count, image filenames, and every image's tags.

---

## A detail that makes the fixture trustworthy

`CharacterFileLoader.loadAllCharacters()` opens a **working-directory-relative** path:

```java
TFile characterFolder = new TFile("characters");
```

So the fixture is generated by running the harness with the working directory set to the game
folder. This is the same quirk flagged as a port hazard elsewhere — here it is what lets us capture
genuine loader output instead of a reconstruction of it.

Two obstacles had to be cleared first:

- The game's `log4j2.xml` writes `jasbro.log` into the working directory. That write is denied when
  the working directory is the install folder. `fixtures/log4j2-harness.xml` redirects logging to
  the console so the harness runs anywhere.
- `javac` on this machine defaults to **MS932**, so the harnesses are compiled with
  `-encoding UTF-8`.

## Trap 1 — image tags are a SET, not a list

The first run reported **64 mismatches**, all of the form:

```
Loli[1] 45.png: tags [VAGINAL,ANAL] != [ANAL,VAGINAL]
```

The C# parser returned tags in file order. The Java loader returned them in a different order.
The natural conclusion — "the loader sorts tags" — would have been **wrong**.

The actual declaration:

```java
private Set<ImageTag> tags = new HashSet<>();
```

and `addTag` guards with `contains` first.

Two consequences:

1. **Tag order is not contractual.** A `HashSet` of enums iterates in the JVM's hash layout —
   an implementation detail of the runtime. We tested this rather than assumed it: generating the
   fixture twice produced byte-identical output, so the order is *stable on this JVM*. That stability
   is precisely what makes it a trap. A test that compared tag order would pass reliably while
   asserting something the game never promised and content authors cannot control.
2. **Tags deduplicate.** A repeated `<tag>` collapses to one. We checked all 506 shipped images and
   found **0 duplicate tags**, so this is latent — but it is real semantics for user-authored
   content.

**Fixes:** `ImageEntry.AddTag` now deduplicates; the verifier compares tags **as sets**;
`ImageEntry` documents that order carries no meaning.

## Trap 2 — images ARE sorted, and the comparison must be ordinal

With tags compared as sets, a *second*, smaller mismatch appeared:

```
Toddler[0]: filename '15.jpg' != '08.jpg'
```

Only `Toddler` was affected — the one character whose on-disk order differs from sorted order. This
was the comparator previously noted as "still needs porting".

```java
public static class ImageDataComparator implements Comparator<ImageData> {
   public int compare(ImageData o1, ImageData o2) {
      if (o1 == o2) return 0;
      else return o1 == null ? -1 : o1.getFilename().compareTo(o2.getFilename());
   }
}
```

It compares **filenames** (not full keys), lexicographically.

> **The port-critical detail:** Java's `String.compareTo` compares **UTF-16 code units**. C#'s
> default string comparison is **culture-sensitive** and would order non-ASCII filenames
> differently — producing a subtly different gallery order, and differently again on a machine
> with a different locale. The port uses `string.CompareOrdinal`, which matches Java exactly.

**Fix:** `CharacterPropertiesParser` now sorts images by `CompareOrdinal(a.Filename, b.Filename)`.

> Aside: the comparator's null guard is **one-sided** — it survives a null `o1` but calls
> `o2.getFilename()` unguarded, so a null `o2` throws. Latent; not reachable from current content.

## What this does and does not prove

**Proven.** For all 10 loadable characters, the C# parser produces exactly what the shipped Java
loader produces from the same files, across every field the loader populates.

**Not covered yet:**
- **11 `properties.xml` exist but only 10 load.** The loader explicitly skips `template`, which
  also lacks images. The port must skip it identically — it does, and the count matches.
- **Only characters.** Items, NPCs, events, quests and rooms are separate loaders, still unported.
- **Only `loadCharacterOptimized`.** The game uses the optimized path (`optimized=true`) at startup;
  the non-optimized path differs in image handling and is not compared.
- **Attribute text fallback.** Legacy looked up each attribute element by enum name and fell back to
  localised text from `TextUtil`. English content matches by name, so the fallback is inert here and
  is not reproduced.

## Reproduce it

```powershell
pwsh -File verify-save.ps1
```

Step 1 regenerates both the save and content fixtures with the real Java classes — including
running the game's own loader over `C:\Games\Jasbro_Final\characters`. Step 2 runs the C# verifier,
which compares against them. The script exits non-zero on any mismatch.
