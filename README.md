# JaSBro R0.1.2 — reverse-engineering analysis and port

**A technical study of an existing game, prepared to support a port away from Java. It is not the
game, and it is not a redistribution of the game.**

<details>
<summary><b>What "reconstructed source" means, precisely</b></summary>

`game-source/` was produced by running **CFR 0.152** and **Vineflower 1.12.0** over the shipped
`JaSBro.jar` (R0.1.2, window title *"Jasbro R0.1.2 final"*). It is **decompiled output, not the
author's original source.**

Consequences to keep in mind:

- **Variable and parameter names are largely lost.** The decompiler invents names where the
  bytecode's local variable table is absent. Do not read meaning into identifiers like `var3`.
- **Some constructs are decompiler artifacts, not author bugs.** `decompiler-output/` contains both
  decompilers' output so the two can be compared — **a construct present in only one is suspect; one
  present in both is almost certainly real.**
- **Lambda bodies, generics and string concatenation may be rewritten** into semantically equivalent
  but differently-shaped code.

A public GitHub fork exists at `https://github.com/kingpingpong/JaSBro` (commit `11a9560`). It is
**not** vendored here, because the shipped build differs from it so heavily that it is a poor
behavioural reference — see [Established facts](#established-facts).
</details>

---

## What this is for

The goal is to **port JaSBro off Java** — to Godot 4.7.2 Mono + C#, with the simulation in a plain
.NET assembly (`port/Simbro.Core`) and Godot as a thin presentation layer.

To do that safely, the behaviour of the existing game had to be established first: what it does, what
it gets wrong, and what a save file and the on-disk content actually mean. That is what this
repository records.

**Reviewing this?** The highest-value places to look are under
[Open questions](#open-questions-where-help-is-wanted).

## Established facts

Verified by experiment. **Please don't re-derive these** — better to spend effort elsewhere. Each has
a reproducible procedure in `analysis/`.

<details>
<summary><b>The decompiled source is faithful — it compiles and runs</b></summary>

- 629 files compile under JDK 8 with **0 errors**, producing 1,637 classes.
- Only **7 classes** needed a decompiler fallback; 1 needed a hand-fix for a CFR artifact
  (`1.$SwitchMap` → `SwitchMapHolder.$SwitchMap`), and 26 "variable already defined" cases needed
  per-case braces restored.
</details>

<details>
<summary><b>The shipped build differs substantially from the public fork</b></summary>

- Shipped: 629 files. Fork: 533. **526 shared, 90 added, 7 removed — and only 9 shared files are
  byte-identical.**
- The shipped build **deleted the entire `jasbro/security/` sandbox**; remaining
  `AccessController.doPrivileged` calls are no-ops.
- Growth: `Attend.java` +70,432 chars (×3.0), `Bartend` +31,353, `AuctionHouse` ×15.1.
- Shrinkage: `Perks.java` −98,834 (perks moved to `perktrees/`), `RoomInfoUtil` −12,013.

**So the fork only helps with provenance** — telling an author bug from a decompiler artifact, and
only on byte-identical hunks.
</details>

<details>
<summary><b>Content is executable, not just data</b></summary>

- 40 XML files contain **166 embedded BeanShell `<code>` blocks** evaluated at runtime.
- Breakdown: 95 expression, 38 script, 21 script+api, 11 simple, 1 api-call — one shared
  `bsh.Interpreter`.
- Blocks call straight into the game API (`data.characters.add(capturedChar)`).
- **Decision: transpile them to C#**, relying on the syntactic closeness of the languages. See
  `analysis/BSH-MIGRATION.md`.
</details>

<details>
<summary><b>Save format is fully characterised, and compatibility is proven both ways</b></summary>

Saves are XStream-serialised `GameData`, written as `save1.xml`/`quicksave.xml` in the working
directory. All verified against fixtures generated by the real Java classes:

- Root element is the **fully-qualified class name** (`jasbro.game.GameData`), not the JAXB name.
- **Null fields are omitted; empty collections are present-and-empty.**
- **Enums are written by NAME** — renaming a constant breaks saves.
- Element name is the type; `class=` attribute for polymorphism.
- XStream **never self-closes** empty elements (`<x></x>`), and the header is
  `<?xml version="1.0" ?>` — note the space before `?>`.
- **`Charakter.base` is `transient`** — the content definition is *not* in the save. A character
  carries its own copies plus a `baseId` link back to its `properties.xml`, so **a save is only
  interpretable alongside the matching content set.**
- References come in **two forms**: indexed (`.../Charakter[2]`, **1-based**) and unindexed
  (`.../Charakter`, first match). Both must resolve to the **same instance**, or cycles explode.
- `AgeProgressionData`'s `WeakReference<Charakter>` **does round-trip** and preserves identity when
  the parent is also in the save. When the parent has been collected it loads as empty — which is
  exactly why the class also carries plain `nameMother`/`nameFather` strings.

**Proven in both directions.** The port writes saves that the *shipped Java game* loads, including a
full character with traits and its content link.
</details>

<details>
<summary><b>Content parsing is verified field-by-field</b></summary>

The C# parser was measured against the **shipped game's own `CharacterFileLoader`** reading the real
content folder: **10 of 10 characters, every field identical** — name, type, gender, specialisation,
attributes, traits, image count, filenames, tags.

Two traps this caught, which a hand-written test would have missed:

- **Image tags are a `HashSet`.** They deduplicate, and iteration order is a JVM hash artifact. It
  *is* stable across runs — which is what makes comparing order a trap. Set semantics are the real
  contract.
- **Images are sorted by filename, ordinally.** Java's `String.compareTo` is UTF-16 ordinal; C#'s
  default is culture-sensitive and would mis-order non-ASCII filenames.
</details>

## Known defects — 151 confirmed

Every finding has a `file:line`, a severity, a confidence, and where possible a fork twin proving it
is author code rather than a decompiler artifact.

**How each is treated is decided, not ad hoc** — see `analysis/PORT-POLICY.md`: *fix crashes and pure
arithmetic; preserve behaviour that shapes game balance, and document every preservation.*

The headline results:

- **Money is created and destroyed in ordinary play.** The engine has a clamped payment API
  (`payFixed` returns what was actually collected) that many callers ignore. Drinks are credited at
  full price to customers who cannot pay; tips read a customer's balance and never charge them; the
  entire GROUP activity path charges customers and credits **nothing**.
- **Two shipped-content defects break a quest in normal play.** `freeBunnysuit.xml` references a
  misspelled `itemId` and sets an out-of-range `questStage`; the quest is marked solved *before* the
  crash, so the reward is permanently lost. Of the 10 distinct item ids referenced by all content,
  **exactly 2 are dangling**. A patch is documented but **deliberately not applied**.
- **Trait effects are enum-initialised singletons holding per-character state**, so one character's
  transformation level is computed from another's. `Trait.setText` mutates JVM-wide enum state.
- **`realestate/` is entirely dead code**, and all 8 marketing Target/Niche perks are no-ops.
- Several crashes are reachable in normal play: out-of-bounds customer indexing, `nextInt(0)` on
  emptied lists, and a `switch` in `BathAttendant` missing every `break`.

## Open questions where help is wanted

These are where an independent look has the most value.

1. **Does the port's save reader handle every reference shape a real save can contain?** Two forms
   are verified (indexed, unindexed) plus a weak reference, but **cross-type cycles are not** — a
   graph closing through a *different* type (house → room → character → house) has never been
   exercised. The fixtures are synthesised; **no real player save exists to test against.**

2. **Is the BeanShell → C# transpilation plan sound?** 166 blocks, 21 mixing script and API calls.
   Two parallel variable stores exist (`CustomQuest.getAttributeMap()` vs `Quest.variables`) and **56
   content elements depend on the split** — `eval("return this.variables;")` reflects over the script
   namespace, so script-assigned variables silently become game state.

3. **Is the bug-fidelity policy right?** `analysis/PORT-POLICY.md` sorts all 151 findings into fix /
   preserve. The balance-versus-bug boundary is a judgement call, and three are flagged as near the
   line: `getResistance` WATER→WIND, `getArmor` discarding ARMORPERCENT, `Reward.skillPoints`.

4. **Is Godot the right presentation target?** The domain assembly is engine-agnostic, so this is
   reversible. The honest concern, in `analysis/ENGINE-CHOICE.md`, is that Godot has **no real data
   grid** while this game is fundamentally *spreadsheets with pictures*. Avalonia UI was considered a
   better technical fit and rejected for wanting game-engine feel.

5. **Never deep-audited:** the GUI, and inventory/economy's interaction with housing. Six audits
   covered business activities, events/housing, content scripting, traits/perks, inventory/economy
   and character lifecycle; the GUI was skipped on the grounds that it is being rewritten.

## Reproducing the verification

`BUILDING.md` has the full procedure. In short, `analysis/verify-save.ps1` runs three stages and
**exits non-zero on any failure**: generate golden fixtures with the real Java classes, check the C#
port against them, then feed C#-written saves back to the real Java game.

**Current state: 125 C# checks + 12 cross-language checks, all passing.**

> Requires the original `lib/` jars and `characters/` folder, which are **not** in this repository.
